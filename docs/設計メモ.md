## 1. 名称

- 正式名：github-ppoi for Fileserver
- 日本語の呼び名（副題）：Githubっぽいのをファイルサーバでやるやつ
- GitHubのリポジトリ名・Goのモジュール名：github-ppoi-for-fileserver
- exe名：github-ppoi.exe
- 端末側の設定・キャッシュ・ツール専用cloneの置き場：%LOCALAPPDATA%\github-ppoi\

## 2. 全体像

- 各メンバーが自分の端末でexeを起動すると、localhost（既定ポート9418）でWeb画面とGitea互換APIが上がり、ブラウザが開く
- データの正本はすべてファイルサーバ上の共有フォルダ（以下、データルート）に置く
- データルートは複数登録でき、1つのデータルートがGiteaの owner（組織）1つに対応する。チームごとに別のフォルダにデータルートを置き、1つの画面で全部をまとめて見る
- コードのgitリポジトリはデータルート配下のベアリポジトリで、各自が従来どおり直接push/pullする
- Issue、Pull Request、コメント、レビュー、添付ファイルは、データルート配下にファイルとして保存する。gitには入れない
- 端末側にあるもの（exe、config、キャッシュ、ツール専用clone）はすべて消えてよい。端末を作り直しても、exeを置いてデータルートを登録すれば元に戻る

## 3. 決定事項

### 3.1 保存の形：フォルダ＋イベント追記

- Issue、コメント、状態変更などはすべて「イベント1件につき1ファイル」の追記で保存し、既存ファイルの上書きは行わない
- 現在の状態（タイトル、本文、open/closed、ラベル、担当など）は、イベントを時系列に適用して組み立てる
- Issue番号の採番は、issuesフォルダ配下に番号のフォルダを「既に存在すれば失敗する」方式で作成し、作成できた側がその番号を取る。次の番号は既存の最大＋1から試し、失敗したら＋1して再試行する
- 番号はIssueとPull Requestで共通の連番とする
- フォルダ名は6桁ゼロ埋め。ツール内部では数値として扱うため、999999を超えた場合は7桁になるだけで動作に影響しない（エクスプローラーの名前順表示が崩れるのみ）
- イベントのファイル名は「UTC時刻（ミリ秒まで）_端末名_プロセスID_プロセス内連番.json」とし、他の端末とも同じ端末の別プロセスとも重複しないようにする
- ファイルの書き込みは一時名で書いてからrenameし、書きかけが他の端末から見えないようにする。一時名は「本来の名前.端末名-プロセスID-連番.tmp」で一意にし、書き終えたときに同じ対象の古い残骸（1時間以上前の .tmp）を消す
- イベントと添付のrenameは、既存のファイルがあれば失敗する呼び出し（MoveFileW。置き換えフラグ無し）を使い、同名のファイルが後勝ちで消えないようにする。上書きファイル（config.json、repo.json、labels.json、users\<ログオン名>.json）は置き換える
- 端末間の時計のずれは許容する。同じIssueを別の端末が数秒以内に操作することは想定しない
- 各端末はローカルにキャッシュを持ち、画面表示のたびにissues配下のフォルダ一覧とeventsの新規ファイルだけを見て差分を読み足す。キャッシュは消してよいものとする

### 3.2 レビューの範囲：Gitea相当

- 差分表示、行コメント、承認／要修正、マージボタンまでを持つ
- IssueとPull Requestは分ける（GiteaおよびGitHubと同じ）。番号は共通連番で、PRは作成イベントにis_pull、head、baseのブランチ名を持つ
- マージはツール専用clone上で行う。fetch→baseブランチにheadをマージ→push。2台が同時にマージした場合は後からpushした側が弾かれるので、それが排他になる。弾かれた側は再fetchしてやり直し、コンフリクトする場合は手で解決するよう画面に表示する
- マージ方式は --no-ff 固定。squash、fast-forwardの選択肢は持たない
- マージ後、リモートのheadブランチは削除する
- マージボタンはGitHubと同じく、押したあとに確認を挟む2段階とする
- マージ済みのPRにはRevertボタンを置く。押すとマージコミットを打ち消すrevertコミットを作ってpushする。マージもrevertも履歴に残る
- Revertは承認の有無にかかわらずbaseにpushする。承認必須の設定はマージにだけ効き、Revertには効かない
- 承認は既定では必須としない。誰でもマージできる

### 3.3 リポジトリごとの設定（既定はいずれもオフ）

- 承認必須：オンにすると、承認が1つ以上無い限りマージボタンが押せない
- 新しいpushで承認を無効にする：承認必須がオンのときだけ意味を持つ。オンにすると、承認したコミットが今の head と同じか、承認した時点と今とで PR の差分（base との差）の中身が同じ承認だけを数える。base を取り込んだだけの push では承認は残り、差分が変わる push や force push（承認したコミットが無くなる）では承認が無効になる。Giteaのブランチ保護「古い承認を取り消す」と同じ。GitHubはコミットが1つでも増えたら無効にするが、そこまでは厳しくしない
- force push禁止：オンにすると、ベアリポジトリに `receive.denyNonFastForwards` を設定し、履歴を書き換えるpushを弾く。ブランチ単位の制御はしない。receive-pack は push した本人の端末で動くため、本人が `-c receive.denyNonFastForwards=false` を付ければ通る。うっかり防止の設定であり、画面の文言とREADMEにその旨を書く
- いずれも meta\<リポジトリ名>\repo.json に持ち、画面のSettingsで変更する

### 3.4 force pushへの対処

- ツールとしてforce pushは禁止しない（3.3の設定をオンにしたリポジトリを除く）
- PRのheadブランチがforce pushされたら、PRの画面に「force pushされた」旨を表示する。古いコミットに付いた行コメントは「古い版へのコメント」として畳んで残す
- 対象のコミットが履歴から消えても表示できるよう、行コメントにはコミット、パス、行番号に加えて差分の断片（当該行の前後数行）も保存する
- 行コメントはコミット単位で判定する。headに新しいコミットが積まれると（force pushでなくても）それまでの行コメントはすべてOutdatedとして畳む。行の内容が同じでも新しいコミットには付け直さない
- ツール専用cloneは、fetchのたびにリモートに強制的に合わせる（`git reset --hard origin/<branch>`）
- マージ済みPRのbaseがforce pushで巻き戻された場合、PRはマージ済みのまま扱う（GitHubと同じ）

### 3.5 Gitea互換API

- ツールはGitea API v1互換のエンドポイントをlocalhostで提供する
- 実装範囲：Issue、Pull Request、Review（承認／要修正／コメント、行コメント）、Labels、Attachments、Repo（読み取り、ブランチ一覧、diff取得）、User（自分の情報）。admin、org、webhook、actions等は実装しない
- /api/v1/repos/{owner}/{repo}/… の owner はデータルートの owner 名に対応する。/api/v1/repos/search と /api/v1/user/repos は全データルートのリポジトリを横断して返す
- 認証はローカルのみのため、トークンは空でなければ何でも受け付ける
- 自分の画面もこのGitea互換APIだけで動かす。画面専用の別APIは作らない
- /api/v1/version はGiteaの版を名乗る値を返し、本ツールのバージョンは別の欄で返す
- Codex向けには、AGENTS.mdに「%LOCALAPPDATA%\github-ppoi\port.txt に書かれたポートで localhost にGiteaがいる、使えるAPIはこれ」と記す形で連携する

### 3.6 データルートのフォルダ構成

```
<データルート>\
  config.json                          ← このデータルートの設定（owner名、表示名、ベースブランチ名、添付サイズ上限など）
  bin\
    github-ppoi.exe                    ← 配布用の最新exe
  repos\
    <リポジトリ名>.git\                ← ベアリポジトリ（各自が直接push/pull。ツールは中身を触らない）
  meta\
    users\
      <ログオン名>.json                ← 表示名（1人1ファイル）
    <リポジトリ名>\
      repo.json                        ← 説明、デフォルトブランチ名、承認必須、force push禁止
      labels.json
      issues\
        000012\
          events\
            20261017T123456789Z_<端末名>_<プロセスID>_001.json
          attachments\
            <時刻または乱数>_<元のファイル名>
```

- owner 名はデータルート側の config.json で決める。端末側では決めない（人によってURLが変わるのを避けるため）
- owner 名はURLに入るためASCII（例：unkan、kiban）とし、表示用の日本語名（例：運用管理、厚木基盤）は別に持つ
- owner 名はデータルートを新規作成するときに入力必須とする。既定値は無い
- 同じ owner 名のデータルートが2つ登録されていたら、起動時にエラーで知らせる
- イベントJSONは `{"type": "...", "user": "...", "time": "...", "body": "..."}` の形で、typeは created／comment／closed／reopened／title／labels／assignees／review／review_comment／merged／edited／deleted を基本とする。本文はMarkdown文字列としてJSON内に持つ。細部は実装時に詰める
- edited は本文またはコメントの編集、deleted はコメントの削除。いずれも対象のイベントのファイル名を持ち、元のイベントは消さずに追記する。表示では最新の本文を出し、編集履歴は畳んで見られるようにする（GitHubと同じ）。削除したコメントは表示しない
- Issue と PR のタイトル、本文、コメントの編集と削除は、作成者本人だけができる。画面と API で同じ
- データルートの config.json は format（データ形式の版、整数）を持つ。exe が知らない format のデータルートは読み取り専用で開き、画面にその旨を表示する

### 3.7 リポジトリの扱い

- ツールは起動時に、登録されている全データルートの repos 配下の *.git をすべて拾って一覧にする。登録作業は無い
- 新規リポジトリは画面から作成する。どのデータルート（owner）に作るかを選び、ツールが repos\<名前>.git に `git init --bare` し、meta\<名前>\ も作る
- 既存のローカルgitリポジトリは、画面で空のリポジトリを作ったあと、手元で `git remote add origin` と `git push --mirror` で履歴ごと移す
- 各自の作業cloneはツールは関知しない。画面にclone用のコマンドを1行で表示し、コピペして使ってもらう。このコマンドにはpush時の所有者チェック対策（remote.origin.receivepackの設定）を含める
- ツール専用cloneは各自の作業cloneとは別に %LOCALAPPDATA%\github-ppoi\repos\<owner>\<リポジトリ名>\ に持つ。無ければツールが作る。画面を開くときに裏でfetchしてから差分を出す

### 3.8 添付ファイル

- 対応する。attachments\ に「時刻または乱数_元のファイル名」で保存し、本文からはGiteaと同じく `![](/attachments/<id>)` で参照する
- APIはGiteaの /issues/{index}/assets に合わせる
- 画面はクリップボードからの Ctrl+V 貼り付けを必須とする（スクリーンショットを貼る用途）。加えてファイル選択でも添付できる。画像以外（Excel、PDF など）も添付できる
- サイズ上限はデータルートの config.json で持つ

### 3.9 ユーザー識別

- Windowsのログオン名（%USERNAME%）をそのまま識別子とし、Gitea APIの login にもそれを返す
- 表示名は本人が画面で一度登録し、登録されている全データルートの meta\users\<ログオン名>.json に書く。自分のファイルだけなので競合しない。読むときは見つかった最初のものを使い、未登録ならログオン名のまま表示する

### 3.10 画面

- GitHubの画面構成と導線をそのまま真似る。GitHubのロゴ（Octocat、Invertocat）は使わない。名前は本ツールの名称の一部として「GitHub-ppoi」と表記してよい。README に GitHub, Inc. との関係を断る一文は置かない
- アイコンはOcticons、CSSはPrimer（いずれもMIT）を使い、すべてexeに埋め込む。外部への参照は持たない。github.com本体のCSSや画像は持ってこない
- Primer CSSは21.5.1に固定する。22では Box、State、TimelineItem、UnderlineNav が削除されており、GitHubの見た目が組めないため
- 画面の文言はGiteaの言語ファイルをそのまま取り込んで使う。go-gitea/gitea の options/locale/ から locale_ja-JP.ini と locale_en-US.ini を取得し（取得元のタグを記録する）、third_party/gitea/locale/ に置いてexeに埋め込む。文言のキーはGiteaと同じものを使う。Giteaに無い本ツール独自の文言は別ファイルに足し、Giteaのファイルは編集しない。既定は日本語で、切替は自分の設定画面に置く
- 画面の一覧
  - トップ：全データルートのリポジトリ一覧を owner ごとにまとめて表示、新規リポジトリ（作成先の owner を選ぶ）
  - 横断ページ：全 owner をまたいだ Issue 一覧と Pull Request 一覧。絞り込みは「すべて」「自分に割り当て」「自分が作成」と、open／closed
  - 新着の印：自分が関わる Issue と PR（自分が作成、担当、レビューまたはコメントしたもの）に、前回開いたあとに増えたイベントがあれば印を付ける。横断ページと各一覧に出す。キャッシュが持つ「前回より増えたイベント」を使い、サーバは要らない
  - 検索：Issue と PR のタイトル、本文、コメントの部分一致。キャッシュ上で行う。全 owner をまたぐ
  - Code：ファイルツリー、ファイル表示、ブランチ切替、コミット履歴、コミットの差分、cloneコマンド、タグ一覧
  - Issues：一覧（open／closed、ラベル、担当で絞り込み）、詳細（本文、コメント、ラベル、担当、クローズ／再オープン、本文とコメントの編集・削除）、新規
  - Pull requests：一覧、詳細（Conversation／Commits／Files changed のタブ、承認／要修正、マージボタン、Revertボタン、コンフリクト時の表示、force pushの表示、本文とコメントの編集・削除）、新規（ブランチを選んで作成）
  - 本文とコメントの編集画面には、新規作成と同じMarkdownのプレビューを付ける
  - Settings：説明、デフォルトブランチ、承認必須、新しいpushで承認を無効にする、force push禁止
  - 自分の設定：データルートの一覧（追加・削除）、表示名、言語
  - Releases：一覧、詳細、新規（3.18）
  - 使用しているOSSとライセンスの一覧ページ
  - 他の端末が書いたものが見えるまで10秒程度かかることを、横断ページに一文で示す
- 実装はGoの html/template でサーバ側でHTMLを組み、差分の行コメント、Ctrl+Vの添付、Markdownのプレビューなど必要な箇所だけJSを使う。SPAにはしない
- Markdownの描画は goldmark、差分は `git diff` の出力をGoでHTMLにする

### 3.11 実装と配布

- 実装言語はGo。Windows用の単一exe
- 開発は家のClaude Codeで行い、ソースは自分のGitHubで公開する
- GitHub Actionsで、タグを打つとWindows用exeをビルドしてReleasesに置く
- 職場ではReleasesからexeを落としてデータルートの bin\ に置き、各メンバーはそこから自分の端末にコピーして起動する。端末を作り直したらコピーし直す
- 端末側の %LOCALAPPDATA%\github-ppoi\config.json はデータルートのパスの一覧を持つ。初回起動時に設定画面でデータルートを1つ以上登録する。追加・削除は自分の設定画面で行う
- ファイルサーバへの書き込み権限の有無はツールでは判定しない。書き込みに失敗したらその場でエラーを表示するだけとし、権限の制御はファイルサーバ側に任せる
- 起動時に bin\ のexeのバージョンが自分より新しければ、画面の上部に「新しい版があります」と表示する。bin\ はどのデータルートのものを見てもよい
- 待ち受けポートの既定は 9418（gitプロトコルの公式ポート）。使用中なら +1 ずつ順に空きを探して上げる（9418〜9427）。上がったポートは画面のフッターと %LOCALAPPDATA%\github-ppoi\port.txt に出し、Codexやteaはそのファイルを参照する
- 端末側の config.json でポートを明示してある場合は、空きを探さずにエラーで止めて知らせる
- 二重起動したときは、既に自分が上がっていることを検知し、ブラウザだけ開いて新しい方は終了する
- 起動時にブラウザを開かないオプション（--no-browser）を持つ
- CSRF対策：画面は Go 標準の http.CrossOriginProtection を通し、別サイトからの書き込みを拒否する。API は URL のクエリでトークンを受けず（Authorization ヘッダのみ）、JSON を受ける経路は Content-Type: application/json を要求する。Hostヘッダが localhost または 127.0.0.1 以外のリクエストは弾く
- ログオン名は環境変数の自己申告であり、ツールは検証しない。READMEに明記する
- データルートに書ける人は、互いの端末で git のコマンドを実行できる関係（safe.directory=* と diff.external 等）にある。この信頼を前提とすることをREADMEに明記する。緩和として、読み取り系の git コマンドには -c diff.external= -c log.showSignature=false を付け、diff には --no-ext-diff を付ける
- リポジトリには .gitattributes を置き、改行はLFに揃える
- ソース、README、テストデータに、職場のファイルサーバのパス、社員番号の形式、リポジトリ名などの職場固有の情報は一切入れない。すべて config.json に逃がす
- gitは各端末のGit for Windowsを呼ぶ。exeには同梱しない

### 3.12 ライセンスの扱い

- 本ツールのLICENSEはMIT。著作権者はGitHubのアカウント名とする
- Gitea APIの形（パス、JSONの項目）は互換実装として参考にする。Giteaのソースコードや言語ファイルを取り込む場合はMITに従い、third_party/gitea/ とライセンス一覧ページに著作権表示とライセンス文を置く
- Octicons、Primer、goldmarkなど使用するOSSは、画面のライセンス一覧ページに著作権表示とライセンス文をまとめて出す

### 3.13 バージョン表記

- 表記は `Ver X.YZ` と、バグ修正を表す英字。`Ver 0.10` から始める
- Z（例：0.10→0.11）：小さい修正
- 英字（例：0.11→0.11A→0.11B）：バグ修正のみ。Zまで行ったらZを上げる（0.11Z→0.12）
- Y（例：0.11→0.20）：大きい修正
- X：`Ver 1.00` は職場で実際に使われた版。使われるまでは 0.x のまま上げていく。1.00以降は、データルート上のデータ形式（フォルダ構成、イベントJSON、config.json の format）に互換性の無い変更でXを上げる。これが上がるときだけ全員同時に更新が必要。0.x の間はそうした変更もYで扱う
- gitのタグは `v0.11A` の形
- exeのVERSIONINFOにも入れる。数値4組の欄は英字を数字に置き換え（0.11A→0.11.1.0）、文字列の欄に `Ver 0.11A` を入れる
- 画面のフッターにも表示する
- 更新通知の比較は bin\ のexeのVERSIONINFOを読んで行う

### 3.14 SMB上の同時更新の検証

- 検証用プログラムは本体と同じ採番・書き込みのコードで作る
- 家の2台のPCとNASで同時に数千回ループさせ、終了後に両方のログを突き合わせて番号の重複が無いことを確認する
- 確認項目
  1. 2台から同時に同じ番号のフォルダを作ったとき、片方だけ成功しもう片方は確実に失敗するか
  2. 一時名で書いてrenameしたファイルが、もう1台から書きかけの状態で見えないか
  3. 片方が作ったファイルがもう片方から何秒で見えるか（WindowsのSMBクライアントはフォルダ一覧を既定で10秒程度キャッシュする。採番の再試行回数と画面の更新間隔に関わる）
- 実行手順は1行貼るだけの形にする
- 合格基準：2台で各1000回の採番を行い番号の重複がゼロ、書きかけのJSONを読んだ回数がゼロ、片方が書いたファイルがもう片方から見えるまでの遅れが30秒以内
- 検証プログラムは、書きかけの読み込みを実際に測れる作りにする。events フォルダを直接走査して .json ごとに読み込みと JSON の解釈を試し、失敗した名前を次の周で再試行して「失敗→成功」の件数を数える。終了後の確認では .tmp の残留と不正な JSON も数える
- あわせて確認する項目：os.Rename が既存ファイルを置き換えるか（Windows では置き換える仕様）、.tmp の残留頻度、端末間の時刻のずれ

### 3.16 インポートとエクスポート

- 形式は Gitea の `dump-repo` / `restore-repo` の形式に合わせる（Gitea の services/migrations/dump.go と modules/migration 配下の構造体。参照した Gitea の版を記録する）
- 対応する方向は3つ。GitHub → 本ツール、本ツール → Gitea、本ツール → GitHub
- `github-ppoi import`：dump-repo 形式のフォルダをデータルートに取り込む。git は bare を push --mirror。Issue と PR の番号は元のまま保つ（番号を指定してフォルダを作る）。作成者は poster_name をそのまま user に入れる。マージ済み PR は merged イベント（merge_commit_sha）にする。レビューの行コメントは diff_hunk を差分の断片として保存する。ラベルとリリースも取り込む。マイルストーンと wiki は読み飛ばし、その旨を表示する
- GitHub からの取り込みは、家で `gitea dump-repo --git_service github --clone_addr <URL> --auth_token <token>` を実行して dump-repo 形式のフォルダを作り、それを職場に持ち込んで import する。本ツールは GitHub の API を叩かない
- `github-ppoi export`：データルートのリポジトリを dump-repo 形式で出す。本物の Gitea に `gitea restore-repo` で流し込める。編集履歴は最新の本文だけを出し、削除済みコメントは出さない
- `github-ppoi export-github`：GitHub の API で Issue と PR を作り、git を push --mirror する。ネットが要るので家で実行する。作成者は API を叩いた本人になるため、本文の先頭に元の投稿者と日時を入れる。番号を揃えるため、欠番は空の Issue を作ってクローズして埋める。マージ済み PR は GitHub で PR として作れないため、Issue として作り「元は PR #N、マージ済み」と記す

### 3.17 番号の予約と整合性チェック

- `github-ppoi reserve`：指定した番号までの空のフォルダを作り、採番を進める。バックアップからの復元で最大番号が巻き戻ったときに使う
- `github-ppoi check`：イベントの JSON が読めるか、添付が存在するか、イベントが持つ SHA が bare にあるか（git cat-file -e）、git fsck を一括で行い、結果を一覧で出す。復元のあとに使う

### 3.18 リリース

- GitHub の Releases に相当する。タグに紐づける
- 項目：タグ、タイトル、本文（Markdown）、添付ファイル、プレリリースの印
- 保存：meta\<リポジトリ名>\releases\<タグ名>\ に、Issue と同じイベント追記方式（created、edited、deleted）で持ち、添付は attachments\ に置く
- タグの作成は、ツール専用 clone で git tag して push する
- API は Gitea の /repos/{owner}/{repo}/releases に合わせる
- 画面は GitHub の Releases を真似る。細部は実装時に詰める

### 3.19 UNC パスのデータルート

- UNC パスで登録したデータルートでは、リポジトリ作成時の `git init --bare` が「fatal: unable to get current working directory: Permission denied」で失敗する。同じデータルートをネットワークドライブで登録し直すと成功する
- 原因は git 側の実装による。git は対象のフォルダへ chdir した後、mingw_getcwd で GetFinalPathNameByHandleW を呼び、失敗すると GetLongPathNameW を呼ぶ。UNC パスではどちらも共有のルートから各階層の親フォルダを照会してパスを組み立てるため、途中に一覧権限の無い階層があると両方失敗する。ネットワークドライブでは照会がドライブのルートより下に限られるため成功する。-C を付けた他の git 操作、clone、push（receive-pack と index-pack）も同じ getcwd を通るため、UNC のままでは同じ理由で失敗する
- 対処として、git に渡すパスの根元をデータルートにする。DefineDosDevice でデータルートごとに DOS デバイス名を定義し、git には `\\.\<名前>\...` の形（以下、仮想パス）を渡す。ネットワークドライブと同じ仕組みだが、ドライブ文字を使わないためエクスプローラーには表示されず、管理者権限も不要で、ネットワーク接続を新たに張ることもない。ログオンセッション内のみの定義で、ログオフで消える
- データルートの読み込み時に、UNC で登録されたデータルートごとに DefineDosDeviceW(0, 名前, UNC パス) を呼ぶ。golang.org/x/sys/windows の DefineDosDevice を使用する。ローカルパスのデータルートには何もしない
- 名前は `github-ppoi-<owner 名>` とする。owner 名は同じ端末で重複しない（同じ owner 名のデータルートは登録できない）ため、同じ端末の他のデータルートと名前が重ならず、同じデータルートはどの端末でも同じ名前になる。config.json には記録しない。連番を振って config.json に記録する方式は、別々の端末で別のデータルートに同じ番号が振られ、両方を登録した端末で衝突するため採らない
- owner 名の末尾が . の場合、`\\.\` のパスでは末尾の . が落ちて別の名前を探しに行くため、DOS デバイス名として使用できない。新しく作るデータルートでは owner 名の末尾の . を弾く（作成時の検査と設定画面の入力形式）。既に末尾が . のデータルートは定義に失敗した扱いとし、画面にエラーを表示して UNC パスのまま使用する
- 既に同名の定義が存在し、同じ対象を指す定義が 1 つだけなら、削除も定義もせずにそのまま使用する（サーバの稼働中にサブコマンドや smbtest が定義し直すと、その間に実行された git が失敗するため）。違う対象を指しているか（データルートを移した後に残った定義など）、定義が積み重なっているときは、DDD_REMOVE_DEFINITION で削除してから定義する
- 定義に失敗した場合は画面にエラーを表示し、そのデータルートは実体の UNC パスのまま使用する
- ツール終了時に定義は削除しない。ツール停止中も Codex 等の git が仮想パスで動作できるようにするため。ログオフで消え、次回起動時に再定義する
- 管理者として実行したプロセスとは定義が別になる（subst と同じ）。README に注記する
- git に渡すパス（-C、init の引数、clone 元、push 先、画面に表示する clone コマンドと push 手順）は、データルートの実体パス部分を `\\.\<名前>` に置き換えた仮想パスにする。ツール自身のファイル操作は実体パスのまま行い、変換は git に渡す箇所に限る。UNC でないデータルートは変換しない
- リポジトリ作成時の `git init --bare` も仮想パスで実行し、他の git の呼び出しと同じ -c（safe.directory=*、core.longpaths=true、core.hooksPath 等）を付ける
- 設定画面のデータルートの入力例は UNC のまま変更しない
- 既存の clone の remote を仮想パスへ付け替える手順（`git remote set-url origin \\.\github-ppoi-<owner 名>\repos\<リポジトリ名>.git`）を README に記載する

## 4. 未決定・未検証の事項

- Gitea公式CLIの tea が、どこまでAPIを揃えれば通るか（実装前に確認）
- push時の所有者チェック対策が、グローバルの `safe.directory *` で済むかどうか（済むならcloneコマンドが短くなる。家の環境で確認）
- SMB上の同時更新（3.14の検証を実施）
- GitHub Actionsのビルド環境でのGoのバージョンとVERSIONINFOの埋め込み方法
- 職場環境で確認すること：未署名のexeを %LOCALAPPDATA% から起動できるか（AppLocker等）、ウイルス対策ソフトがGo製のexeを誤検知しないか、端末が1人1VMか、%LOCALAPPDATA% が端末の作り直しまで残るか、共有フォルダにオフラインファイルが効いていないか、Git for Windows の版（--initial-branch は 2.28 以上、merge-tree --write-tree は 2.38 以上）
- 1人1VMが必要な理由：ツールは接続元が 127.0.0.1 であることだけを見て、その端末にログオンしている本人の操作とみなす。RDS や Windows 11 マルチセッションのように1台のOSに複数人がログオンする環境では、同じ端末の別のユーザがそのポートに接続でき、起動した人の名義で書ける。別サイトからの書き込み拒否はブラウザ経由の攻撃を防ぐもので、直接アドレスを打つ操作には効かない。1人1VMでない環境で使うなら、起動時に乱数のトークンを作って URL に付け、最初のアクセスで Cookie にする方式（Jupyter と同じ）が要る
- DFS レプリケーションと多重ターゲットは不可。採番は mkdir の排他、イベントの書き込みは置き換え無しの rename に依存しており、DFS レプリケーションやストレージ側の双方向複製があると複製の間で番号が重複する。DFS 名前空間は単一ターゲットなら問題ない。サーバの移設に備え、データルートは最初から名前空間のパスで登録する
- FSRM のファイルスクリーンが共有上の exe を弾く設定になっていないか。弾くなら bin\ 経由の配布（3.11）は使えず、署名証明書を取るか管理者が Program Files 配下に置くかを先に決める
- ファイルサーバの監査ログ（ファイルシステムの監査。イベント 4663）が有効か。ログオン名は端末の USERNAME の自己申告なので、誰が書いたかの裏付けは NTFS のファイル所有者と監査ログしかない
- バックアップの方式と対象。データルートはフォルダ1つで完結するので既存のサーバのバックアップに含める。bare リポジトリはファイルを順に写す方式（robocopy 等）だと push の途中と重なって壊れた複製になり得るため、シャドウコピーのようなスナップショット方式にする。除外設定で *.git フォルダが抜けていないかも確認する。復元の手順は README の「バックアップと復元」に書く
- 端末の時刻同期。イベントの順序は各端末の UTC 時刻で決まるので、ドメインの Kerberos が許す5分のずれの範囲で、返信が元のコメントより前に並ぶことがある。監査の時系列に使うなら注意する
- Git for Windows が日本語Windowsで日本語のメッセージを出すか（ツールは LC_ALL=C を付けて呼ぶので影響しない想定）
- dump-repo 形式の細部が Gitea の版で変わるか（export の出力を実際の Gitea に restore-repo して確かめる）
- UNC で登録したデータルートで、リポジトリ作成、clone、push が仮想パスで通るか（3.19）。自宅では上位階層の権限構成を再現できないため、最終確認は職場で行う
